# Лабораторная работа № 7

## Параллельный FastAPI-сервис и мониторинг дрейфа

**Вариант:** 18 — классификация текстов 20 Newsgroups
**Модель:** `v1`
**Среда:** macOS, Python 3.12, 8 логических CPU
**Основные библиотеки:** FastAPI, `joblib==1.6.0`, `evidently==0.7.23`

## 1. Цель работы

Реализовать пакетный инференс в FastAPI с использованием `joblib`, сравнить задержку и пропускную способность при разном числе исполнителей, настроить мониторинг дрейфа входных характеристик и предсказаний модели, проверить обработку ошибочных запросов и устойчивость сервиса.

## 2. Реализация пакетного сервиса

Создан маршрут `POST /predict/batch`, принимающий массив текстов и число исполнителей `workers`. Входные данные валидируются Pydantic; число исполнителей ограничено количеством логических CPU. Для получения предсказаний используется активная модель из реестра ЛР6. Параллельная обработка реализована посредством `joblib.Parallel` и `joblib.delayed` в **потоковом режиме** (`prefer="threads"`).

Используется существующая инфраструктура ЛР6, включая реестр модели, метрики и маршрут проверки состояния. Контракт отдельных текстов предусматривает ограничение до 20 000 символов. В мониторинге предсказаний тексты перед отправкой в API обрезались до этой длины; это ограничение необходимо учитывать при интерпретации эксперимента с увеличением длины текста.

## 3. Сравнение производительности

### 3.1. Методика

- Оборудование: 8 логических CPU.
- Размер пакета: 32 текста.
- Число исполнителей: 1, 2 и 4.
- Прогрев: **2 запроса** на режим, согласно сохранённому выводу и CSV.
- Измерения: **30 повторений** для каждого режима.
- Метрики: средняя клиентская задержка, P95 клиентской задержки, пропускная способность (текстов/с), ускорение относительно одного исполнителя.

### 3.2. Результаты

| Исполнители | Средняя задержка, мс | P95, мс | Пропускная способность, текстов/с | Ускорение |
|---:|---:|---:|---:|---:|
| **1** | **5,200** | **6,208** | **6153,35** | **1,000×** |
| 2 | 14,389 | 15,252 | 2223,85 | 0,361× |
| 4 | 14,289 | 15,140 | 2239,45 | 0,364× |

В данной конфигурации последовательная обработка оказалась быстрее параллельной: при двух исполнителях средняя задержка увеличилась приблизительно в 2,77 раза, при четырёх — в 2,75 раза. Вероятное объяснение — накладные расходы на планирование небольших задач и работу потоков; отдельно причины замедления не профилировались. Вывод относится к исследованной модели, размеру пакета и оборудованию и не распространяется автоматически на более тяжёлые модели.

**Исходные измерения:** `reports/LAB7/parallel_benchmark.csv`.

## 4. Мониторинг дрейфа

### 4.1. Методика

Для каждого сценария сформирован поток из 800 объектов. Первые 400 объектов — базовый поток; с объекта 400 вводится изменение. Используются скользящие окна по 200 объектов с шагом 100. За эталон принимается отдельная выборка из 400 объектов. Для сравнения распределений рассчитывается PSI, сигнал дрейфа возникает при **PSI > 0,5** хотя бы по одной контролируемой характеристике. Формируются CSV-таблицы и HTML-отчёты Evidently.

Контролируемые **входные характеристики**: `word_count`, `char_count`, `top_vocab_share`, `source_class`. Последняя характеристика — исходный класс генератора данных, а не предсказание модели.

Контролируемые **выходные характеристики**: `predicted_class` и `confidence`, полученные через HTTP API модели `v1`.

Сценарии: неизменённый поток (`clean`), увеличение длины текстов (`length`), изменение долей тематических классов (`class_shift`) и изменение словаря (`vocabulary`).

### 4.2. Результаты

| Сценарий | Входной дрейф | Дрейф предсказаний | Ложные тревоги до изменения, входы / выходы |
|---|---|---|---:|
| `clean` | Не обнаружен | Не обнаружен | 0 / 0 |
| `length` | Обнаружен, задержка 200 объектов | Не обнаружен | 0 / 0 |
| `class_shift` | Обнаружен, задержка 200 объектов | Обнаружен, задержка 200 объектов | 0 / 0 |
| `vocabulary` | Обнаружен, задержка 100 объектов | Обнаружен, задержка 200 объектов | 0 / 0 |

Задержка считается как конец первого окна с сигналом минус позиция начала изменения (400). Например, обнаружение в окне 300–500 соответствует задержке 100 объектов, хотя окно включает только первые 100 изменённых объектов.

### 4.3. Интерпретация

Мониторинг входных данных обнаружил **3 из 3** искусственно внесённых изменений. Мониторинг выходов обнаружил **2 из 3**: сдвиг тематических классов и изменение словаря. При увеличении длины текстов распределения предсказанных классов и уверенности модели существенно не изменились по выбранному порогу PSI. Это не означает отсутствия входного дрейфа и не доказывает неизменность качества классификации: оценка качества требует истинных меток и соответствующих метрик.

На чистом потоке ложных тревог не наблюдалось. В исследованных сценариях до начала инъекции ложных тревог также не зарегистрировано.

**Исходные данные:** `drift_metrics.csv`, `drift_summary.csv`, `prediction_drift_metrics.csv`, `prediction_drift_summary.csv`.
**Визуальные отчёты:** `evidently_*.html`, `predictions_*.html`.

## 5. Проверки и отказоустойчивость

Проведены автоматические проверки пакетного маршрута: последовательный и параллельный запрос, отклонение пустого текста, ограничение числа исполнителей, обработка исключения отдельной задачи с последующей проверкой доступности сервиса и успешного следующего запроса.

- **ЛР7:** 5/5 тестов пройдены.
- **Регрессионные тесты ЛР6:** 18/18 пройдены.
- **Ruff:** `All checks passed!`.

**Ограничение отрицательного теста:** при использовании `joblib` с `prefer="threads"` моделируется исключение в задаче, но не принудительное завершение отдельного процесса-исполнителя. Если критерий лабораторной требует именно остановку процесса, необходим дополнительный эксперимент с процессным пулом; текущий тест не следует выдавать за такую проверку.

## 6. Воспроизводимость

Команды выполняются из корня репозитория после создания и активации виртуального окружения и подготовки артефактов модели ЛР6 и исходных данных генератора ЛР5.

Установить зависимости:

```bash
python -m pip install -r requirements.txt
```

Запустить сервис в отдельном терминале:

```bash
python -m uvicorn src.lab7.service:app --host 127.0.0.1 --port 8000
```

Запустить эксперименты и проверки:

```bash
python -m src.lab7.benchmark
python -m src.lab7.drift_monitor
python -m src.lab7.prediction_monitor
python -m pytest tests/lab7 tests/lab6 -v
python -m ruff check src/lab7 tests/lab7
```

## 8. Вывод

Реализован пакетный FastAPI-сервис с параллельным выполнением задач через `joblib`, проведено сравнение режимов обработки, создан мониторинг входных данных и предсказаний. Эксперимент показал, что при коротких запросах параллельность может снижать производительность. Контроль входных данных позволил выявить изменения, которые не проявились в распределении предсказаний. Совместный мониторинг обоих уровней обеспечивает более полную картину поведения сервиса.
